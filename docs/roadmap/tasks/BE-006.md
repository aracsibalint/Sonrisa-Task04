# BE-006 — Atomic event acceptance/manual admin input

Status: **Not started (approval/dependency gated)**

## Objective
Implement the shared bounded acceptance use case: synchronously validate and match a new event, then atomically commit event identity and complete durable channel intents containing matching/rule snapshots. Expose it first through admin manual input. No separate matching table is created.

## Approval gates

## Scoped steps
1. Route each manual category through the same normalized validation/acceptance service future adapters will call; enforce Admin and configured manual source identity.
2. Validate bounded input, acquire the outer gate, inspect durable identity and load bounded current eligible rules within the approved transaction boundary.
3. Return the existing event for an equivalent duplicate; reject conflicting controlled/manual reuse without overwriting or evaluating new rules.
4. Evaluate pure predicates and freeze event/rule/version/filter/recipient/rendered-payload snapshots. Produce one intent per selected channel and no intent for a nonmatch.
5. Enforce complete fan-out, outstanding-intent and retained-intent admission; persist event/seen identity as applicable and all intents with embedded matching/rule snapshots in one transaction. There is no separate match insert. Success is returned only after commit; no external I/O occurs under gate/transaction.
6. Implement sanitized outcome/error reporting and narrow fault-injection seams for transaction/restart tests; no separate asynchronous matching queue.

## Detailed edge-case tests
- Admin submits valid matching/nonmatching manual events for each category; non-admin/anonymous requests persist nothing. Equivalent normalized data produces the same predicate result regardless of ingress provenance, with provenance kept distinct.
- Fail before event insert, after event insert, after in-memory matching/snapshot construction, between selected-channel intent inserts and before commit: every stage rolls back all related persisted rows/identity. Retry then succeeds once. Commit followed by lost HTTP response returns the original event on retry without reevaluating rules or adding intents. No fault point presumes a separate Match table.
- Same source/key/equivalent payload, concurrent duplicate requests and restart/retry yield one durable event and one rule/event/channel intent. Different content under the same controlled key conflicts; same key in another configured source remains distinct. Manual keys include the authenticated actor per the canonical model: two admins can use the same caller ID without collision, and caller-supplied actor spoofing is rejected.
- A later retry of an already accepted immutable payload remains idempotent even after its original freshness window, following canonical duplicate-before-relative-freshness handling. New stale events still fail; auth/schema validation is never bypassed.
- Arrange rule mutation/event races explicitly: old rule commit before event, event before mutation, paused/deleted rules and resumed rules. Results follow successful commit order, not HTTP start or provider occurrence time. Prior accepted events never replay.
- No matching rules still yields an evaluated durable event with canonical evaluation metadata; email-only/Slack-only/both fan-out is exact. Later rule/destination changes cannot rewrite snapshots.
- At active-rule/fan-out/outstanding/retained limits, reject or defer the entire event if full fan-out cannot fit; no partial channels or seen marker persists. Retained-intent saturation pauses ingestion for operator review without deleting history or stopping existing delivery/rule administration. Gate waiter saturation/timeout/cancellation and SQLite lock error return canonical retryable failure without false success; the next eligible operation can proceed.
- Escaped news/control-character/numeric payloads cannot inject message markup/headers; logs contain identifiers and sanitized failure classes rather than recipient secrets or full message bodies.

## Completion criteria
Admin acceptance works for all categories through one shared use case; real SQLite fault/race/dedup/capacity evidence proves all-or-nothing acceptance and snapshot semantics. No sender is needed to prove durable intent creation. Independent consistency/security review and shared completion record are complete.

## Excluded work
