# BE-005 — Owner rule APIs/provisioned channels

Status: **Not started (approval/dependency gated)**

## Objective
Expose the approved owner-only rule lifecycle with typed filters and selection of already provisioned channels, preserving versioned future-event semantics.

## Explicit dependencies
- [BE-002](BE-002.md), [BE-003](BE-003.md) and [BE-004](BE-004.md) complete.
- Read [requirements](../../requirements/alerts-mvp.md), [scope](../../process/approved-scope.md), [overview](../../architecture/overview.md), [flows](../../architecture/processing-flows.md), [data](../../data/data-model-and-evolution.md), [API](../../api/backend-api-design.md), [security](../../architecture/security.md) and [ADRs](../../adr/README.md). Use canonical route/DTO/version/error contracts exactly.

FR-002, FR-003, FR-005, FR-009, FR-010; NFR-001, NFR-003 / AC-002, AC-003, AC-005, AC-009, AC-010, AC-011, AC-013.

- `src/Alerts.Api/Rules/`: canonical endpoint/DTO mapping and bounded paging.

## Approval gates
- Confirm approved route shapes, error/owner-concealment behavior, version/conflict handling, quotas and soft-delete rules.
- Application-managed Rule Version is established by ADR-003; use the forthcoming schema/API's reconciled version/ETag preconditions. Commit ordering chooses the rule version for an event; stale-client rejection protects rule edits. Neither implies a last-write-wins alternative.
- Align quota counting with the recovery overview's active-rule limits and enforce creation/activation under the gate; the inspected schema/API still count larger undeleted-rule sets including paused rules.
- Accept that pause/delete affects future event acceptance, not already committed intents, and that create/edit/resume never replays history.
- Provisioned destination references may be selected only through approved channel names; any destination management behavior is a separate scope change.

## Scoped steps
1. Implement owner-derived create/list/detail/update/pause/resume/delete using canonical contracts; pause/resume uses the canonical update shape, not invented additional routes. Never accept a caller-selected owner ID. Expose the canonical current-owner channel-availability read without addresses or secret references.
2. Enforce ownership in Application and query scope as well as endpoint policy; Admin inspection permissions do not enable cross-owner writes.
3. Validate exactly one category/filter, at least one supported available channel, active-rule quotas on creation/activation and canonical version rules before committing under the single gate. Do not silently apply superseded undeleted-rule caps.
4. Resolve provisioned channel availability without exposing secret URLs or permitting user input to redirect delivery.
5. Apply versioning/soft deletion and audit relationships; preserve future-event semantics without adding a replay path.
6. Provide bounded deterministic list behavior and sanitized validation/conflict responses; add integration evidence for the complete actor matrix.

## Detailed edge-case tests
- User A completes the lifecycle; user B cannot list/read/change/pause/resume/delete A's rule by guessing IDs; Admin receives no cross-owner edit privilege. Anonymous requests fail.
- Reject owner spoofing, source/destination URL fields, missing/wrong/multiple filter variants, unknown channel and unavailable email/Slack. Both available channels are accepted; duplicates follow canonical validation rather than creating duplicate delivery work.
- Validate trimmed keyword and numeric boundary errors through the API without persisting a rule; quota overflow creates no extra active rule. Concurrent create/activate/resume operations at the last active quota slot cannot exceed the cap; paused-rule behavior matches the reconciled canonical active-quota policy.
- Concurrent edits/stale version, repeated pause/resume/delete, update of a deleted rule and missing ID follow canonical status/version behavior; no lost update or resurrected soft-deleted record.
- Seed stored events/intents with embedded matching/rule snapshots as relational fixtures: create/edit/resume causes no reevaluation or new intent, pause/delete preserves prior snapshots. No separate match rows are needed. BE-006 will verify actual race ordering with newly accepted events.
- Paging bounds, empty lists, ownership filters and sanitized errors remain correct; response/log snapshots contain no destination secrets.

## Completion criteria
The approved owner lifecycle and provisioned-channel validation work through real authenticated endpoints; cross-owner/admin bypass tests and quota/version races pass; no historical reevaluation or destination CRUD exists. Review, risk-relevant audit and shared completion record are present.

## Excluded work
Source/destination CRUD or UI, editing others' rules, event ingestion, historical replay, notification cancellation, richer filters, frontend and cross-tenant behavior.
