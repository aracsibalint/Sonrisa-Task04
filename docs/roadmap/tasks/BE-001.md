## Approval gates
- Before creating/restoring project dependencies, record user acceptance of the architecture/ADRs/contracts and exact compatible SDK/package/test-tool versions, licences and support expectations.
- Approve the recovery overview's EF Core/Identity/OpenAPI/test packages, MailKit, AngleSharp and pinned sandbox receiver inventory; installing a new package is not implied by the product's stack choice. Parser selection is proposed, not undecided, and its exact pin/licence still needs acceptance.
- Resolve environment-specific local storage/key protection and sandbox configuration assumptions. Live providers may remain blocked and disabled.

## Scoped steps
1. Inspect repository instructions/status and preserve parallel/user changes. Record approved choices and unresolved gates.
2. Scaffold the module references in the overview: Domain pure, Application depends on Domain, Infrastructure implements ports, API composes one host.
3. Pin the approved toolchain/dependencies; establish consistent compiler/nullability settings and repeatable restore/build/test entry points.
4. Add configuration sections/options boundaries and safe examples, keeping source URLs/destinations centrally configured and live enablement off pending approval.
5. Establish actual test discovery and an initial meaningful host/module-boundary check. Do not create placeholder passing tests or empty implementations to simulate completeness.
6. Document clean-checkout commands, prerequisites and which later tasks supply persistence, auth, ingestion and delivery.

## Detailed edge-case tests
- Restore/build on a clean checkout using the pin; unsupported/missing SDK produces a clear setup failure rather than silently choosing a different major version.
- Validate forbidden module references through build/project inspection; Domain has no EF/Identity/HTTP/hosting dependency and only one deployable application is introduced.
- Check source-controlled config and generated outputs for example-only credentials, database files and Data Protection keys; actual secrets must not enter the repository.
- Start the scaffold with approved development defaults and verify it does not poll live sources or send messages before those features/gates exist.
- Confirm a failing discovered test fails the test command during harness setup, without retaining a deliberately failing test; record actual output rather than assuming discovery.

## Completion criteria
Approved dependencies and module graph are recorded; clean restore/build and meaningful discovered checks pass; startup/configuration limits are documented; no runtime feature completion is claimed. Independent review and the shared completion record are present.

## Excluded work
Domain predicates, schema/migrations, seeded accounts, endpoints, workers, provider calls, frontend, additional deployment units and production deployment.
