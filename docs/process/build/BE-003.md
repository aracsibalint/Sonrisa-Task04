### Fix and policy

- `AlertsDbContext.ValidateWrite` now requires emergency intent originals already InFlight with a claim/lease and count1..5. Current count must be identical, Version increments exactly once, destination state is Delivered/Failed/RetryScheduled and claim/lease must be cleared. Pending/RetryScheduled->InFlight, count increases and claim rotation cannot use emergency admission.
- Before saving, each modified intent requires exactly one modified **existing** InFlight attempt in the same save. Original and persisted intent/attempt evidence must agree on IDs, token, ordinal/count, lease and intent original Version (plus immutable attempt start); stale/detached fabricated EF originals cannot authorize an unpersisted claim. No new emergency rows. The pair saves atomically in the existing admitted transaction, without gate reacquisition.
- Allowed pairs: Delivered/Succeeded; RetryScheduled/TransientFailure or OutcomeUnknown with count1..4; Failed/PermanentFailure with count1..5, or Failed/TransientFailure or OutcomeUnknown only at count5. Completion finishes the existing attempt rather than appending an OutcomeUnknown row. No new retry/send begins under emergency admission.
