## Delivered behavior

- Explicit startup provisioning validates stable lowercase GUIDs, normalized unique emails, User/Admin roles and the configured Identity password policy. Hashes are computed before admission; one normal admitted transaction creates users/memberships idempotently. Existing passwords are not overwritten and conflicts abort without partial state.
- Login reads and verifies the framework password hash outside admission, then reloads hash/security/concurrency/lockout state under the singleton gate. Changed state causes bounded outside re-verification. Failed counters/lockout/reset use emergency Identity bookkeeping; rehash uses normal admission. Token issuance occurs only after the admitted commit/checkpoint succeeds.
- Generic401 covers unknown, wrong and locked accounts. Five failures lock for15 minutes. Built-in fixed-window limiter is10/minute/IP, queue0.
- Owner policy permits User or Admin; Admin policy requires Admin. Admin receives both claims but no ownership bypass. `/me` is claim-derived; `/me/channels` is no-tracking and redacted.
- Persistent keys require an absolute separate directory and stable application name whenever persistence is configured, and are current-user DPAPI protected. Unconfigured host keeps liveness but login/readiness unavailable.

### Decision and implementation

- DECISION Level1: centralized `SqliteStorageFailures.IsStorageAvailability`. It masks the reported extended result to its low-byte primary and includes only BUSY5, LOCKED6, READONLY8, IOERR10, FULL13 and CANTOPEN14. Every included category latches `StorageAdmission`; the unit of work translates it to safe503.
- DECISION Level1: NOMEM7 is excluded because it indicates process-memory health rather than durable storage availability. ERROR1, CORRUPT11, CONSTRAINT19, MISUSE21 and NOTADB26 are also excluded. They propagate through normal safe exception handling/startup failure and do not acquire the transient storage latch from this classifier.
- FACT: both direct `SqliteException` and EF `DbUpdateException` inner-SQLite filters in `PersistenceUnitOfWork` and `AlertsDbContext` use the same predicate.
- FACT: the existing valid-password real writer-lock test still proves BUSY -> latched503/no token. A new admitted-operation integration test executes invalid SQL to produce actual direct SQLITE_ERROR1 and performs an EF duplicate-role save to produce wrapped actual CONSTRAINT19; both propagate unchanged and leave storage unlatched.
